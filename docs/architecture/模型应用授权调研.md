# Black God 模型应用授权调研

核对日期：2026-09-09。范围：官方文档与本地源码，只读调研；未进行真实账号登录或修改授权代码。

## 结论

Minis 确实实现了浏览器授权、自动接收结果、保存凭据与令牌刷新。应把这套体验拆成各服务商独立适配器。OpenRouter 有明确面向第三方应用的 PKCE 授权换 Key 流程，是 Black God 第一条免手填密钥路线。Codex、Kimi、Gemini CLI 的自身登录机制不能直接等同于普通第三方产品可自由复用的通用模型API授权。

## 已核对的源码

OpenMinis 本地提交：4ef29002e88db1e20e462ec2ff46916e8a7dcb45。

- src/ios/Providers/OpenRouter/OAuth/OpenRouterOAuthManager.swift：login 从45行开始，生成PKCE，启动localhost:3000/callback，展示SFSafariViewController，等待最多300秒，用code和verifier换API Key，96行保存到按连接区分的Keychain，defer关闭窗口与监听。
- src/ios/Providers/OpenAI/OAuth/CodexOAuthManager.swift：localhost:1455/auth/callback；校验state；保存access/refresh token；临近过期刷新。
- src/ios/Providers/OAuthRefreshSingleFlight.swift：每个连接同一时间只执行一次刷新，多个请求等待同一结果。
- src/ios/Providers/Kimi/OAuth/KimiDeviceFlow.swift：设备码授权，处理pending、slow_down、过期和取消。
- 本地Codex codex-rs/login/src/server.rs：PKCE、随机state、精确回调校验、令牌换取；device_code_auth.rs提供设备码路线。
- 本地Hermes hermes_cli/auth_codex.py：设备码登录、令牌刷新、轮换失败处理。

源码不能直接照搬：本地Minis Android OpenAI管理器在state不匹配时仍继续；iOS OpenRouter调试日志会打印换Key响应内容。Black God应拒绝不匹配回调，所有构建都不记录凭据和授权码。这里只是针对实际授权路径的发现，不是完整安全审计。

## 厂商差异与官方依据

| 服务 | 官方机制 | Black God判断 |
|---|---|---|
| OpenRouter | 第三方PKCE授权，回调code换用户API Key | 最适合优先实现；不是取得每家大厂的独立Key |
| Codex | ChatGPT浏览器登录及设备码登录，保存/刷新凭据 | 可参考或评估官方Codex集成；尚未确认Black God独立通用模型客户端的授权资格 |
| Claude | 原生应用订阅OAuth与开发者API认证分开 | 官方明确不允许第三方提供Claude.ai登录并代用户转发订阅凭据；Black God采用官方API或受支持云服务 |
| Kimi Code | RFC8628设备码授权，浏览器确认后CLI自动收取令牌 | 可参考体验；Black God独立接入范围需进一步确认 |
| Gemini CLI | Google登录、Gemini API Key、Vertex AI认证 | Google登录不自动等于Gemini通用API权限，需区分目标服务与授权范围 |

## Black God拟采用流程

用户选择连接 → 打开官方授权页面 → 用户登录并同意 → 返回一次性授权码 → App校验会话并换取凭据 → 原子保存连接与Keychain凭据 → 查询可用模型 → 显示连接结果并回到任务页。

OpenRouter返回的是API Key，不能假设它有refresh token；OAuth服务则需要独立处理过期、刷新轮换和撤销。设备码授权可以自动识别授权成功，但自动切回App仍取决于浏览器返回路径，不能把后台轮询成功等同于已经实现自动跳转。

iOS优先评估系统认证会话与服务商支持的返回地址，不能凭空假定任何服务商都接受blackgod自定义scheme。公开HTTPS回调需要实际域名及关联配置；本地回调需要监听范围、端口冲突、后台暂停和超时验收。连接验证先用模型列表等不生成内容的接口，额外付费推理测试需明确呈现。

当前Black God已有手填密钥、Keychain保存、多厂商配置和模型查询基础；以上自动授权尚未实现或实网验收。用户账号登录和授权同意仍需用户完成。
